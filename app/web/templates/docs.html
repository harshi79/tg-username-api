TG Username API

Public-presence intelligence for Telegram usernames. For each username the API normalizes and validates the input, checks whether the handle publicly resolves on Telegram (t.me), and — when it does not — checks whether it exists as a collectible on Fragment with its public marketplace/auction state and TON price when displayed. The API reads only public web pages: no Telegram account, bot token, TON wallet or Fragment login is required.

Verdicts are conservative: a username is reported available only when every public source provides a clean negative response, without any upstream failure. Everything else resolves to safe statuses — and ambiguous evidence always becomes unknown.

Rate limits

25 requests per IP address per minute, applied to /api/* routes (website pages and static assets are exempt).
  • The limiter uses fixed one-minute windows per client IP.
  • One bulk HTTP request counts as one API request against the IP quota — the per-username effort inside a bulk call is bounded server-side instead (maximum 15 usernames per bulk request, limited upstream concurrency).
  • Every API response carries X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset (unix epoch) headers.
  • When the quota is exceeded the API returns HTTP 429 with the structured error body below and a Retry-After header.
  • Serverless note: the limiter is in-memory and therefore best-effort per instance; across a fleet of Vercel instances the effective global quota can be higher. A shared backend (e.g. Redis) can be plugged into the isolated storage layer (app/ratelimit.py) when strictly-global enforcement is needed.
HTTP 429 body
{
  "success": false,
  "error": {
    "code": "rate_limit_exceeded",
    "message": "Rate limit exceeded. Try again shortly."
  }
}

Statuses

StatusMeaning
taken The username currently resolves on Telegram — public channel/group/bot page, or a Fragment "claimed" report that is consistent with Telegram's bare user page.
fragment_collectible Not publicly resolving on Telegram, but Fragment tracks it as a collectible (on_auction, for_sale, sold, available-to-auction, or unavailable/held). Not freely claimable.
available Telegram clearly does not resolve the handle (HTTP 404 or redirect to telegram.org) and Fragment has no page for it, with no upstream errors. Availability can change at any moment; claim it in the official Telegram app to confirm.
invalid Input failed local validation (see Telegram's public rules: 5–32 chars, a–z, 0–9, underscore, starting with a letter). No external request was made.
unknown The API could not safely determine the state. Causes include Telegram's ambiguous bare pages (rendered identically for private-profile users and unclaimed handles), timeouts, rate limits, anti-bot pages and unexpected upstream responses. Never treat unknown as available.

POST /api/v1/check/bulk

Check several usernames concurrently with bounded upstream concurrency. Maximum 15 usernames per request — enforced on the server. Input order is preserved; duplicates share one upstream lookup. One bulk call counts as one rate-limited API request.

cURL
curl -X POST "https://host/api/v1/check/bulk" \
  -H "Content-Type: application/json" \
  -d '{"usernames": ["yorivex", "@yorixa", "https://t.me/yorzen"]}'
JavaScript (fetch)
const res = await fetch("https://host/api/v1/check/bulk", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ usernames: ["yorivex", "@yorixa", "https://t.me/yorzen"] })
});
const data = await res.json();
console.log(data.total, data.results.map(r => r.result.status));
Python (requests)
import requests

data = requests.post("https://host/api/v1/check/bulk",
                     json={"usernames": ["yorivex", "@yorixa", "https://t.me/yorzen"]},
                     timeout=60).json()
print(data["total"], [r["username"] for r in data["results"]])
example response (shape)

Error reference

Transport-level errors are always JSON with success: false:

HTTPerror.codeWhen
400payload_too_largeBulk request with 16+ usernames.
401unauthorizedAPI-key auth enabled and key missing/invalid.
422validation_errorMissing/incorrect request shape.
429rate_limit_exceededMore than 25 requests in the current minute window.
500internal_errorUnexpected server error. Retryable.

Source-level errors (Telegram/Fragment) never change the HTTP status and never become an availability verdict — they are reported inside telegram.error / fragment.error: upstream_timeout, upstream_rate_limit, upstream_blocked, upstream_server_error, upstream_unrecognized_response, network_error.

Reliability rules

  • Telegram not resolving does not mean available — Fragment is checked, and both sources must be cleanly negative for an available verdict.
  • Telegram renders identical bare pages for private-profile users and unclaimed handles (verified 2026-07-30) — those yield unknown, never a guess.
  • Network failures, timeouts, rate limits and unrecognized upstream pages degrade to unknown.
  • Prices and bids are copied from public Fragment listings only — never estimated. The heuristic score in reports resembles rarity, not value.
  • Results are cached briefly (5 minutes by default) because ownership can change at any time.
