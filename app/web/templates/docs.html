Introduction

TG Username API provides public-presence intelligence for Telegram usernames. For each input, the API normalizes and validates the username, checks whether it publicly resolves on Telegram (t.me), and — when it does not — checks whether it exists as a collectible on Fragment with its public marketplace/auction state and TON price when displayed.

The API reads only public web pages. No Telegram account, bot token, TON wallet, or Fragment login is required. Verdicts are conservative: a username is reported available only when every source provides a clean negative response.

Currently no API key is required — authentication can be enabled server-side via the API_KEYS environment variable if needed.

Authentication

By default, the API requires no authentication. All endpoints are publicly accessible. Optional API key authentication can be enabled by setting the API_KEYS environment variable (comma-separated) and the API_KEY_HEADER header name (default: X-API-Key).

Base URL

All API endpoints are rooted at:

https://tg-username-api.vercel.app/api/v1

Machine-readable contract: /openapi.json · Swagger UI at /swagger · ReDoc at /redoc.

Rate Limits

25 requests per IP address per minute, applied to /api/* routes only. Website pages and static assets are exempt.
  • The limiter uses fixed one-minute windows per client IP.
  • One bulk HTTP request counts as one API request against the IP quota.
  • Every API response includes X-RateLimit-Limit, X-RateLimit-Remaining, and X-RateLimit-Reset (Unix epoch) headers.
  • Exceeding the quota returns HTTP 429 with a structured error body and Retry-After header.
  • On serverless platforms the in-memory limiter is best-effort per instance; a shared Redis backend can be plugged into app/ratelimit.py for strictly global enforcement.
HTTP 429 response 
{
  "success": false,
  "error": {
    "code": "rate_limit_exceeded",
    "message": "Rate limit exceeded. Try again shortly."
  }
}

Bulk limits

Maximum 15 usernames per bulk request (HTTP 400 payload_too_large beyond that).

Statuses

StatusMeaning
taken Resolves on Telegram (channel, group, bot) or Fragment "claimed" report consistent with Telegram.
fragment_collectible Not publicly resolving on Telegram, but Fragment tracks it as a collectible (on_auction, for_sale, sold, available-to-auction, or unavailable/held). Not freely claimable.
available Telegram clearly does not resolve the handle (HTTP 404 or redirect to telegram.org) and Fragment has no page, with no upstream errors. Can change at any time.
invalid Input failed local validation. No external request was made.
unknown Could not safely determine state. Never assume availability from this status.

GET /api/v1/check

Normalize, validate and check one username against Telegram — and Fragment only when it does not resolve.

Parameters

NameInTypeDescription
username query string (required) durov, @durov, or https://t.me/durov

Possible errors

422 validation_error · 400 payload_too_large · 429 rate_limit_exceeded · 500 internal_error. Upstream errors never change the HTTP status; they appear inside telegram.error / fragment.error.

Parameters

Same as /check: username (query, required).

POST /api/v1/check/bulk

Check several usernames concurrently with bounded upstream concurrency. Maximum 15 usernames per request. Input order preserved; duplicates share one upstream lookup. One bulk call counts as one rate-limited API request.

Request body

application/json
{
  "usernames": ["yorivex", "@yorixa", "https://t.me/yorzen"]
}
cURL
curl -X POST "https://tg-username-api.vercel.app/api/v1/check/bulk" \
  -H "Content-Type: application/json" \
  -d '{"usernames": ["yorivex", "@yorixa", "https://t.me/yorzen"]}'
JavaScript
const res = await fetch("https://tg-username-api.vercel.app/api/v1/check/bulk", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ usernames: ["yorivex", "@yorixa", "https://t.me/yorzen"] })
});
const data = await res.json();
console.log(data.total, data.results.map(r => r.result.status));

GET /api/v2/resolve

Advanced input resolver that accepts usernames, numeric Telegram IDs, and Telegram deep links through one unified endpoint.

Supported input forms

Input FormatExampleClassification
usernamedurovusername
@username@durovusername
t.me URLhttps://t.me/durovusername
numeric user ID7728424218user_id
tg:// deep linktg://openmessage?user_id=7728424218user_id

How it works

Username inputs (@durov, https://t.me/durov) are forwarded to the existing v1 checker — the response includes the full v1_check result with Telegram and Fragment data.

Numeric user IDs (7728424218, tg://openmessage?user_id=7728424218) are validated for syntactic correctness only. Telegram does not expose public profile information for numeric user IDs through any legitimate public mechanism — numeric ID resolution requires an authenticated Telegram session. The API clearly returns resolved: false for numeric IDs and never fabricates profile data.

Important: Numeric Telegram IDs are never sent to Fragment for lookup. Fragment checking is username-only.

Parameters

NameInTypeDescription
query query string (required) Username, @username, t.me URL, numeric Telegram ID, or tg:// deep link
cURL — username
curl "https://tg-username-api.vercel.app/api/v2/resolve?query=@yori"
cURL — user ID
curl "https://tg-username-api.vercel.app/api/v2/resolve?query=7728424218"

Error Reference

Transport-level errors always return JSON with success: false:

HTTPerror.codeWhen
400payload_too_largeBulk request with 16+ usernames.
401unauthorizedAPI-key auth enabled and key missing/invalid.
422validation_errorMissing or malformed request.
429rate_limit_exceededMore than 25 requests in the current minute.
500internal_errorUnexpected server error. Retryable.

Source-level errors (Telegram/Fragment) never change the HTTP status or become an availability verdict — they appear inside telegram.error / fragment.error: upstream_timeout, upstream_rate_limit, upstream_blocked, upstream_server_error, upstream_unrecognized_response, network_error.
